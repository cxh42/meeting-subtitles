# 设计笔记

> 这份文档记录的是**为什么这样做**——每个不显然的选择背后踩过的坑。
> 想直接用请看 [README.zh-CN.md](../README.zh-CN.md)。


在 Zoom / Teams / Google Meet 开会时，屏幕底部浮一条字幕：上行英文原文，下行中文翻译。
全程本地运行，不调用任何 API。会议结束后自动生成 Markdown / SRT / JSON 转录和 wav 录音。

```
┌──────────────────────────────────────────────────────────────┐
│ ● 录制中  12:34              暂停  原文  A−  A+  ✕           │
├──────────────────────────────────────────────────────────────┤
│  …so we need to update the deployment pipeline before Friday │
│  ……所以我们需要在周五之前更新部署流水线                          │
└──────────────────────────────────────────────────────────────┘
```

## 它是怎么工作的

```
系统声音 (对方说的话)  ┐
                      ├─ 混音 → 16kHz 单声道 PCM
麦克风 (你说的话)      ┘          │
                                  ▼
                        ws://127.0.0.1:8000/asr?language=en&target_language=zh
                                            │
                        WhisperLiveKit (large-v3 + NLLB-1.3B, 本地 GPU)
                                            │
                        ┌───────────────────┴───────────────────┐
                        ▼                                       ▼
                  悬浮字幕窗口                        transcript.md / .srt / .json
```

对方的声音抓的是**输出设备本身在放的东西**，也就是"你听到的一切"。所以它抓的不只是
会议软件——Zoom、Teams、浏览器里的 YouTube、本地播放器、任何正在出声的程序都一样，
不需要它们提供插件或权限。看英文视频想配实时中文字幕，也是同一套东西
（那种场景把「同时录制我的麦克风」关掉即可）。

PipeWire 不需要特殊处理：它自带一个 PulseAudio 兼容层（`pipewire-pulse`），
Ubuntu 22.10 起默认启用，所以 `pactl` 和 ffmpeg 的 `pulse` 输入在两者上都一样能用。

## 使用：点图标就行

安装一次桌面入口：

```bash
./install.sh
```

之后在 GNOME 应用列表里搜「会议字幕」启动（右键图标 →「添加到收藏夹」可钉在侧边栏）。

界面按 Ubuntu 设置的样式做：配色是从 `gnome-control-center` 暗色窗口上**逐像素取的**
（标题栏 `#222222`、卡片 `#272727`、内容区 `#2c2c2c`、Ubuntu 橙 `#e95420`），
结构用 GNOME 的 boxed list——圆角卡片、发丝分隔线、左标签右控件。

```
┌───────────────────────────────────────┐
│  ● 转录引擎已就绪          [关闭引擎]   │
├───────────────────────────────────────┤
│  会议名称              [           ]   │
├───────────────────────────────────────┤
│  录制麦克风                      (●)  │
│  整句润色                        (●)  │
│  CS / AI 术语                    (●)  │
│  字幕大小        ────●────────   20   │
│  字幕透明度      ────────●────  94%   │
├───────────────────────────────────────┤
│          [    开始会议    ]           │
│          [  打开转录文件夹  ]           │
└───────────────────────────────────────┘
```

按「开始会议」后启动器自动隐藏，屏幕底部出现字幕条。点字幕条上的
「结束并保存」结束录制，启动器带着转录路径回来。所有设置都会记住。

**转录引擎完全不用你操心**：启动器发现引擎没跑就自己拉起来，界面显示加载进度。
引擎会留在后台以便下次秒开；想释放显存就点「关闭引擎」。

### 命令行方式（可选）

不想用 GUI 也可以直接跑：

```bash
.venv/bin/meeting-subtitles-engine    # 终端1，开一次整天不用关
.venv/bin/meeting-subtitles-run           # 终端2，每次开会时跑
```

### 常用参数

```bash
# 给出会议里会出现的术语和人名，显著提高专有名词识别率
.venv/bin/meeting-subtitles-run --context "Kubernetes, Anirudh, Prometheus, SLO, canary rollout"

# 只转录对方，不录自己的麦克风
.venv/bin/meeting-subtitles-run --no-mic

# 指定标题（决定保存目录名）
.venv/bin/meeting-subtitles-run --title "Sprint Sync"

# 字幕更大、窗口更宽
.venv/bin/meeting-subtitles-run --font-size 24 --width-ratio 0.9

# 不要悬浮窗，只在后台记录转录
.venv/bin/meeting-subtitles-run --no-overlay

# 看看有哪些音频源可选
.venv/bin/meeting-subtitles-run --list-devices
```

完整参数：`.venv/bin/meeting-subtitles-run --help`

## 输出

每场会议一个目录，默认在 `~/Meetings/2026-09-05_1430_会议记录/`：

| 文件 | 内容 |
|---|---|
| `transcript.md` | 带时间戳的中英对照记录，直接阅读或整段喂给 LLM 做纪要 |
| `audio.wav` | 16kHz 原始录音，事后可以用更大的模型重新转录 |

默认只写 Markdown 一种。需要别的格式时再加：

```bash
.venv/bin/meeting-subtitles-run --formats md,srt        # 配合录屏做字幕
.venv/bin/meeting-subtitles-run --formats md,srt,json   # json 每段含 speaker/start/end/text/translation
.venv/bin/meeting-subtitles-run --no-audio-file         # 不留录音
```

转录文件每 3 秒原子写入一次，中途断电或强杀进程也不会丢失已有内容。

## 提高印度等口音的识别准确率

按效果排序：

1. **传术语表**。口音重的时候，Whisper 最容易错的是专有名词和缩写。CS / AI 的通用
   术语已经内置（见「领域术语」一节），你只要补上**参会人名字和项目名**：
   ```bash
   .venv/bin/meeting-subtitles-run --context "Anirudh, Priya, Project Helios"
   ```
   GUI 里就是「术语 / 人名」那个框。
2. **锁定语言为 `en`**（默认已锁定）。自动语言检测在重口音上容易误判成别的语言，
   一旦判错整段就废了。
3. **戴耳机**。用外放时麦克风会把对方的声音再录一遍，同一句话被转录两次，
   而且叠加后的音质会明显拖低识别率。
4. **模型选择**。`large-v3` 是本地口音鲁棒性最好的选择。如果嫌延迟高，
   `.venv/bin/meeting-subtitles-engine --model large-v3-turbo` 快很多但重口音下会掉准确率。

## 两级翻译：草稿 + 整句润色

字幕的中文行有两种状态，颜色不同，你一眼能分辨：

| 颜色 | 含义 |
|---|---|
| **灰色** | 服务器的流式草稿——边说边译，会跳字、会锁死错误的词序 |
| **黄色** | 整句说完后由本地 LLM 重新翻译的定稿——完整、通顺、术语正确 |

为什么需要两级：服务器的流式翻译是**前缀提交**，句子还没说完就把前几个中文词冻结了，
而且 NLLB-1.3B 在长复合句上会提前吐出结束符，**直接把整个从句丢掉**。实测：

```
EN        : ...update the deployment pipeline before Friday,
            otherwise the canary rollout will block the release.
NLLB 流式 : 所以我们需要更新部署管道,否则, 雀鸟的推出将阻止发布.
Qwen3 整句: 所以我们需要在周五之前更新部署流水线，否则灰度发布将会阻塞发布。
```

术语差距同样明显：`canary rollout` → 雀鸟的推出 vs **灰度发布**，
`bottleneck` → 瓶 vs **瓶颈**，`shipped` → 运送 vs **上线**，
`staging cluster` → *整句丢失* vs **预发布集群**。

润色在**一句话说完之后**才触发（ASR 开始下一句时，前一句就不会再变了），
所以完全不影响实时性——你先看到灰色草稿跟上节奏，一两秒后它变成黄色定稿。
`--context` 里的术语表会作为提示传给润色模型，人名和缩写会被正确保留。

术语表送给识别模型时会包成一句完整的话（`The following is a meeting transcript.
Terms that appear: …`），而不是裸的逗号列表。Whisper 把提示当作前文续写，风格会
被带过去：实测用裸列表时，语音开始前它会先凭空补出一段列表
（"YouTube, YouTube.com/NorthstarIT And."），还会多出 `*sad music continues*`
这类非语音标记；包成句子后两者都消失。

**性能**：Qwen3-4B-Instruct，每句 **0.12-0.40 秒**，模型加载 8.5 秒（会议开始时后台加载，
不阻塞）。显存峰值 **21.5GB / 32GB**。

关掉它（省约 8GB 显存、只保留灰色草稿）：GUI 里关掉「整句润色」开关，
或命令行加 `--no-refine`。

## 翻译质量的现实预期

开启整句润色后，中文定稿（黄色）已经相当可靠。但**灰色草稿只是让你跟上节奏用的**，
不要据此做判断——它会丢从句。关键结论以英文原文（上行，始终显示）或黄色定稿为准。

想再提升一档，可以把润色模型换成 8B：

```bash
.venv/bin/meeting-subtitles-run --refine-model Qwen/Qwen3-8B     # 需先下载，显存约 +16GB 而非 +8GB
```

32GB 显存下 8B 大约会到 30GB，比较紧张，浏览器再占一点就可能 OOM。4B 已经足够好。

## 非语音噪声过滤

Whisper 是在字幕数据上训练的，所以它会照着字幕员的习惯输出 `(cough)`、`[Music]`、
`*clears throat*` 这类提示，在嘈杂的会议麦克风下尤其多。这些不是话，还会各自占一行
字幕、各自触发一次重译。

过滤器**认的是括号而不是词**：括号里的 cough 是字幕提示，句子里的 cough 是有人在
谈论咳嗽——后者不会被动。唯一不带括号也会被丢的，是整段内容除了这个词什么都没有的
情况（比如整句就是 `Cough.`）。

## 断句：按标点，不是按停顿

服务器只在 VAD 检测到停顿时才开新段。真实会议里大家几乎不停顿，结果整段讨论
会被压成一个没完没了的长句——难读，而且作为重译的单位也太大。

Whisper 本身就会输出标点，所以句子边界其实就在文本里。客户端会按 `.` `!` `?` 重新
切分（`i.e.`、`Dr.`、单字母缩写不会被误切；`Yeah.` 这种碎片会并入相邻句）。
好处有三个：

- 字幕一次显示一句，读得完
- 一句话说完就立刻定稿并重译，不用等到说话人停顿
- 转录文件按句分段，时间戳按字符位置在原段内插值

Whisper 大多数时候会给标点，但语速快、不停顿时它可能一整段都不打句号。所以还有一层
**按长度的兜底切分**：超过 140 字符就在最合适的位置断开，优先找逗号分号，其次找
"and then / but / so / because / you know" 这类话语标记，都没有才退回词边界。实测一段
326 字符、全程无标点的话会被切成三句，断点落在 "and then"、"and it turns out"、
"and I think" 上。

想沿用旧行为：`--no-sentence-split`。停顿阈值仍可调：

```bash
.venv/bin/meeting-subtitles-engine --pause-seconds 2.0   # 只影响服务器的粗分段
```

## 字幕条的三行布局

```
┌──────────────────────────────────────────────────────────────┐
│ ● 录制中 12:34         历史 暂停 原文 A− A+   结束并保存      │
├──────────────────────────────────────────────────────────────┤
│ 微调完那个数据集后，注意力权重看起来相当退化。                  │ 黄 · 定稿，常驻
│ ──────────────────────────────────────────────────────────── │
│ So the ablation study shows that removing the retrieval...   │ 白 · 正在说
│ 所以消融研究表明去掉检索部分 会让准确                          │ 灰 · 流式草稿
└──────────────────────────────────────────────────────────────┘
```

每一行能显示多少字是**按当前字体实测宽度算出来的**，不是写死的字符数——所以你调大
字号或换屏幕时，字幕不会撑出窗口把下半截顶到屏幕外。每行最多占两行，超出的部分
在开头用 `…` 表示已截断。

**黄色那行是常驻的**，会一直停留到下一句润色完成为止——早期版本里它只在下一句
很短时才显示，一闪就没了，根本来不及读。

- **历史** 打开可滚动的完整转录窗口，能往回翻本场所有内容，带自动滚动开关
- **结束并保存** 结束本次转录并写盘（右上角只有这一个结束入口，不会误以为是隐藏）
- **原文** 隐藏英文行，只看中文
- **暂停** 冻结字幕（转录和录音继续）
- **◐+ / ◐−** 调整透明度，默认 0.80，可以看见字幕条盖住了什么

透明度有个限制要知道：X11 下 Tk 只能做**整窗透明**，文字会跟着背景一起变淡，
做不到"背景透明、文字不透明"。0.80 是实测下可读性和透视的平衡点。

## 历史窗口

「历史」按钮打开本场完整转录，按聊天软件的规矩工作：

- **向上滚 = 完全冻结。** 新内容一个字都不会写进窗口，只在标题栏累计
  「已暂停 · N 条新内容」。你看的位置纹丝不动。
- **底部浮出「↓ 跳到最新」**，点一下补齐所有新内容并跳到最新，恢复跟随。
- 自己滚回底部也会自动恢复跟随。

渲染是**追加式**的：只有真正变化的那几段会重画，其余部分在 Text 里原地不动。
早期版本每次都整体重建再按滚动**比例**还原位置——内容变多后同一个比例指向的是
不同的行，所以字会在你眼皮底下往上爬。

## 圆角窗口

字幕条、历史窗口和启动器都是圆角的，和 GNOME 其它窗口一致。

实现上不能只靠画：窗口的直角必须从**窗口区域本身**里挖掉，用的是 X11 的 SHAPE
扩展（`python-xlib`）。两个坑：Tk 的 `winfo_id()` 返回的是内层内容窗口，真正显示
在屏幕上的是它的父窗口，贴错了不报错也不生效；而 mutter 会自己管理它画的边框形状，
所以启动器改用 `_MOTIF_WM_HINTS` 去掉系统标题栏、自绘一个（这也正是 GNOME
自家应用的做法），窗口仍然可以 alt-tab。

Wayland 会话下这套仍然有效：Tk 是跑在 XWayland 上的 X11 客户端，
mutter 会尊重 XWayland 表面的形状。

没有 X11 或没装 `python-xlib` 时自动退化成直角，不会报错。
如果哪台机器上去装饰的表现不对，设 `MEETING_NATIVE_FRAME=1` 可以整体退回系统标题栏。

## 领域术语

默认按 **CS / AI 研究** 领域配置，内置 62 个术语，两处生效：

- **识别**：术语表传给 Whisper 做条件化。缩写和专有名词（LoRA、RLHF、vLLM、KV cache、
  NeurIPS、arXiv、FLOPs）不再被音译成乱七八糟的词。常见英文单词不放进去——
  Whisper 本来就认得，塞进去反而稀释了对难词的条件化。
- **翻译**：润色模型拿到该领域的中文对照规范。实测效果：

```
attention weights   → 注意力权重        ablation study → 消融实验
fine-tuned          → 微调              scaling law    → 缩放定律
retrieval component → 检索模块          rebuttal       → 反驳
hallucination rate  → 幻觉率            baseline       → 基线
KV cache / GPU / OOM → 保留英文
```

「train a model」会翻成**训练**模型而不是培训。

你自己的人名、项目名写在「术语 / 人名」框里，它们排在内置词表**前面**——
服务器对该参数有 1000 字符上限，超出时从尾部按术语边界截断，你填的内容一定保留。

不是这个领域时：GUI 里关掉「CS / AI 领域术语」，或 `--domain general`。

## 中文字体 / HiDPI

Anaconda 自带的 `libtk8.6.so` **完全没有链接 Xft 和 fontconfig**，只能使用 X core
位图字体——它根本看不见系统里的 Noto CJK，界面中文会全部渲染成方块。Ubuntu 自己的
`libtk8.6.so` 是带 Xft 的（`tk8.6` 包，通常已装），只是 `python3-tk` 没装所以用不上。

程序启动时会自己检测：如果当前 Tk 认不出任何中文字体，就带上系统 Tcl/Tk 的
`LD_PRELOAD` 重启一次自己（只重启一次，有环境变量兜底）。**不需要 sudo，也不需要
你做任何事。** 转录服务器进程会被显式剥掉这个 preload——PyTorch 没理由把 Tcl/Tk
拖进自己的地址空间。

另外界面尺寸会按屏幕 DPI 缩放。Tk 的字号按磅计算会随 DPI 自动放大，但 Canvas 的
几何是原始像素、不会跟着变；在你这块 165 DPI 的 4K 屏上，不做缩放会导致按钮文字
溢出到背景外面。

## 为什么它启动时不联网

模型下载完之后，服务器每次启动都是**完全离线**的（`HF_HUB_OFFLINE=1`），并且会主动
清空代理变量。原因不是洁癖，是这台机器上 `huggingface.co` 被 DNS 污染，解析到一个
黑洞地址：

```
$ getent hosts huggingface.co
2a03:2880:f11f:83:face:b00c:0:25de   ← Facebook 的地址段
```

huggingface_hub 默认每次加载都会联网校验缓存文件。直连这个地址不会被拒绝、只会被
丢包，于是 TCP 一直停在 `SYN-SENT`，表现就是「加载模型」转几分钟没有任何反应，而
显存和磁盘读取都是零。启动脚本会先检查三个模型是否都在本地，是就直接离线启动，
冷启动 15-40 秒。

## 从图标启动 vs 从终端启动

**GNOME 从应用列表启动的程序不会继承 `~/.bashrc`**，所以你 shell 里的代理设置对它
完全不可见。`install.sh` 会在安装时把当时的代理记录到：

```
~/.config/meeting-subtitles/env
```

这个文件只在**需要下载模型**时才起作用；模型齐全后走离线路径，代理根本不参与。
换了代理端口就编辑这个文件。

注意 GNOME 的代理设置给出的是 `socks://` 而 httpx 只认 `socks5://`，脚本会自动
纠正——否则引擎会直接崩在 `Unknown scheme for proxy URL` 上。

## 网络代理

一个很容易踩的坑：大写的 `HTTPS_PROXY` 和小写的 `https_proxy` 可能指向不同端口，
而其中一个已经失效了。huggingface_hub 内部的原生 HTTP 客户端（Rust/Go 写的那些）
只读大写变量，于是模型下载会卡死，而你 shell 里的 `curl` 一切正常。
`serve.py` 启动时会把大写变量对齐到小写的值，但发现这种情况时最好顺手把
shell 配置里失效的那个改掉。

另外 HuggingFace 的 Xet 传输后端在本地代理下会反复超时，脚本已默认设置
`HF_HUB_DISABLE_XET=1` 走普通 HTTPS 通道。

## 已知限制

- 只支持 Linux（PulseAudio / PipeWire）。macOS 需要 BlackHole 一类的虚拟声卡，
  Windows 需要 WASAPI loopback 后端，两个都没做。
- 悬浮窗依赖 X11 的置顶特性。GNOME 的 Wayland 会话下没问题——Tk 跑在 XWayland 上，
  置顶和圆角都正常。真正没有 XWayland 的纯 Wayland 环境下窗口可能不置顶，
  这时用 `--no-overlay` 只记录转录。
- 单路混音意味着转录里分不出谁说的话。需要区分说话人的话，
  引擎加 `--diarization` 启动（需要额外安装 `diarization-sortformer` 依赖）。
- 中文语音不会被正确转录：源语言锁定为英文。这是准确率和灵活性的取舍。
  如果确实需要中英混说，用 `meeting-subtitles-engine --language auto` 启动，
  但重口音下的语言误判会拉低整体准确率。
- 长时间静音时 Whisper 偶尔会幻觉出短句（实测出现过 "You know"）。
  真实会议有持续的环境底噪，这个问题比纯数字静音下轻得多。
